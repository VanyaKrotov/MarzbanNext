# MarzbanNext

MarzbanNext — самостоятельно разворачиваемая веб-панель для управления пользователями,
подписками и распределённой инфраструктурой Xray. Администратор подключает серверы,
задаёт их конфигурацию, выдаёт пользователям доступ и следит за состоянием узлов и
потреблением трафика из одной панели.

Проект развивается как форк Marzban с разделением управляющего и транспортного уровней.
Master-панель хранит данные и управляет инфраструктурой, а пользовательские подключения
обслуживает Xray на удалённых узлах Marzban-node. На master-панели ядро Xray не запускается.

## Для кого предназначен продукт

Основной сценарий — администрирование собственной Xray-инфраструктуры с несколькими
узлами, в том числе у разных провайдеров и в разных странах. Панель позволяет задавать
разные конфигурации серверов и управлять доступом пользователей без ручного изменения
учётных записей на каждом узле.

| Участник | Задачи |
| --- | --- |
| Sudo-администратор | Управлять инфраструктурой, администраторами, общими настройками, хостами и шаблонами подписок |
| Администратор | Управлять пользователями в пределах своих прав и просматривать доступную статистику |
| Пользователь подключения | Получить ссылку подписки или конфигурацию и использовать её в совместимом клиентском приложении |
| Разработчик интеграции | Автоматизировать операции через REST API, CLI и webhook-уведомления |

Пользовательская учётная запись Xray и учётная запись администратора панели — разные
сущности. Получение подписки не предоставляет административный доступ.

## Какие задачи решает панель

- Централизует выдачу, изменение и отзыв доступа к нескольким Xray-узлам.
- Управляет сроками действия, лимитами трафика и состояниями пользователей.
- Разделяет серверную конфигурацию и параметры, которые пользователь получает в подписке.
- Формирует подписки для разных клиентских приложений из общих данных пользователей и хостов.
- Показывает состояние узлов, ошибки, логи и статистику для диагностики инфраструктуры.
- Позволяет изменять конфигурацию конкретных узлов и перезапускать только затронутые подключённые узлы.

## Основные сущности

| Сущность | Значение в продукте |
| --- | --- |
| Master-панель | Backend, dashboard и база данных с пользователями, конфигурацией, назначениями, статистикой и сертификатами |
| Нода | Удалённый сервер Marzban-node, на котором работает Xray |
| Пользователь | Учётные данные подключения, разрешённые протоколы и инбаунды, лимиты, срок действия и статистика |
| Инбаунд | Серверная точка входа Xray с протоколом, транспортом и параметрами безопасности |
| Аутбаунд | Правило выхода трафика из Xray, используемое конфигурацией узла |
| Правило маршрутизации | Условие обработки и направления трафика; порядок правил имеет значение |
| Хост подписки | Клиентское представление инбаунда: адрес, порт, название, дополнительные параметры и доступные форматы подписки |
| Группа хостов | Группировка хостов для организации и фильтрации выдаваемых подключений |
| Шаблон подписки | Полная клиентская конфигурация или обёртка ссылок определённого формата |
| Составная конфигурация | Шаблон подписки, объединяющий разрешённые подключения в нативные группы или балансировщики клиента |
| Сертификат ноды | Сертификат, связанный с узлом и доступный для назначения TLS-инбаундам |

## Основные сценарии

### Подключение инфраструктуры

Sudo-администратор разворачивает master-панель, создаёт административную учётную запись
и устанавливает Marzban-node на сервере. Для подключения ноды используется сертификат
панели. После подключения администратор назначает узлу нужные инбаунды, аутбаунды,
правила маршрутизации и сертификаты.

Назначения явные: создание ноды или конфигурационной сущности само по себе не связывает
их друг с другом. Нода получает предназначенную ей конфигурацию.

### Выдача и обслуживание доступа

Администратор создаёт пользователя, выбирает доступные протоколы и инбаунды, задаёт
лимит трафика и срок действия. Пользователю передаётся ссылка подписки, ссылка
подключения или QR-код для импорта в клиентское приложение.

В дальнейшем администратор может изменить доступ, отключить пользователя, сбросить
трафик или отозвать подписку. Поддерживаются состояния active, disabled, limited,
expired и on-hold, а также периодический сброс трафика.

### Настройка клиентских подписок

Sudo-администратор задаёт хосты подписки и выбирает для каждого хоста доступные форматы
и шаблоны. При запросе подписки панель учитывает разрешённые пользователю инбаунды,
состояние хостов, выбранные группы и настройки генераторов.

Формат определяется по поддерживаемому User-Agent или явно задаётся в URL.
Каталог содержит пять форматов: `v2ray`, `v2ray-json`, `clash`, `sing-box`, `outline`.
Clash Meta (Mihomo) использует единый YAML-генератор и формат `clash`;
Base64 применяется как кодирование результата URI-подписки.
В API, URL подписок и привязках шаблонов принимаются только эти пять имён.
Алиасы `json`, `xray-json`, `singbox`, `clash-meta` и `mihomo` отклоняются.

Полные шаблоны редактируются отдельно от общих настроек генераторов.
Для sing-box, Clash и Outline используется текущий default соответствующего формата;
смена default применяется к существующим подпискам при следующем запросе.
Для URI и Xray JSON сохраняются персональные шаблоны хостов: смена default влияет
на новые хосты, а изменение текста привязанного шаблона — на следующую генерацию.

В каталоге текущий default каждого формата отмечен заполненной звездой. Выбор другого
шаблона заменяет default только этого формата. Текущий default нельзя снять или удалить.
Его можно переименовать: привязки хостов и статус default сохраняются.
При создании шаблона смена формата заменяет содержимое редактора стартовым шаблоном
выбранного формата.

Форма создания хоста содержит примечание с переключателем включения справа, инбаунд,
группы и строку адреса с портом справа. Дополнительные поля добавляются кнопкой «+»
в разделе «Дополнительно» через меню с группировкой по назначению. Уже добавленные
поля исключаются из меню. Персональные шаблоны URI и Xray JSON выбираются через
комбобокс с группировкой по форматам и чипсами `format:name`; удаление чипа исключает
формат из подписки хоста. Для sing-box, Clash и Outline доступны только переключатели
форматов; общий шаблон выбирается отметкой default в каталоге.
Boolean-параметры задаются переключателями слева от названия: включённый сохраняет
`true`, выключенный — `false`. Удаление динамического поля возвращает значение по умолчанию.
ALPN задаётся мультиселектом; сохранённые нестандартные значения остаются доступны.
Fingerprint выбирается из списка профилей; справка поясняет варианты отдельными пунктами. Сохранённые значения
вне списка остаются доступны при открытии хоста. Текстовые поля показывают примеры
ввода, а иконка информации справа от названия открывает справку для сложных форматов.
Параметры клиента задаются JSON-объектом. Для JSON-полей хоста (параметры клиента,
XHTTP extra, MUX, SockOpt, Final mask и Mapper) кнопка «Настроить»
справа от названия открывает отдельный диалог с Monaco Editor и схемой параметров из API.
«Сохранить» применяет JSON к форме хоста; «Отмена» и закрытие диалога отменяют правки.
Описание сервера задаётся ключом `server_description` в параметрах клиента.
Оно автоматически добавляется только для User-Agent поддерживаемых расширенных клиентов
(FlClash X, Flowvy, prizrak-box, koala-clash, Happ, INCY). В Xray JSON используется
`meta.serverDescription` всей конфигурации, в Clash — `serverDescription` конкретного proxy,
в URI/Base64 — суффикс с Base64-описанием. Для составного Xray-профиля описание берётся
у хоста-получателя. Пустое описание не выдаётся; sing-box и Outline его не получают.
Схема преобразований хоста описывает четыре семейства вывода и отдельные варианты
`set`, `copy`, `unset` с проверкой обязательных полей, подсказками источников и примерами.
Схема Final mask описывает поддерживаемые TCP/UDP-маски Xray, параметры QUIC/TLS,
заголовки и шумовые пакеты; редактор и API проверяют структуру и значения.
Final mask передаётся только в Xray JSON. Сохранённые прежние имена параметров поддерживаются.
Параметры сокета проверяются по схеме Xray с подсказками TCP/DNS-настроек,
Happy Eyeballs, системных ограничений и вариантов `customSockopt` (`int`/`str`).
Та же схема применяется к вложенному `echSockopt`; исходное написание сохранённых ключей сохраняется.
Добавленные текстовые поля сохраняют значение инпута, включая пустую строку.
Пустой SNI задаётся обычным полем SNI без отдельного переключателя.
Удаление поля возвращает наследование. Дополнительные параметры XHTTP задаются единым объектом `extra`.
Его схема описывает HTTP-метод, padding, сессию, размещение данных, XMUX и отдельный
download stream с TLS/REALITY, параметрами сокета и Final mask. Monaco и API проверяют
типы, допустимые значения, диапазоны и конфликты; совместимость с режимом инбаунда
проверяется сервером. Числа и исходное написание диапазонов сохраняются, включая
устаревшие параметры прежних настроек. Справочник: [XHTTP extra](docs/xhttp.md).
В списке хостов отображается заданный порт хоста или текущее значение порта инбаунда.
ID хоста виден в таблице, мобильной карточке и заголовке диалога редактирования.
Хост описывает одно подключение; связей и настроек балансировки на нём нет.
Флаг «Скрыть из списка» выключен по умолчанию и исключает отдельное подключение
из всех форматов подписок, включая URI/Base64 и Outline. Скрытые хосты остаются
доступны для составных конфигураций через директивы `marzban`.
Outline сохраняет один SS-объект из видимых подключений.

Составные конфигурации настраиваются в полных шаблонах через директивы `marzban`:
Xray — `injectHosts`, Clash — `include-proxies`, sing-box — `includeProxies`.
Источники выбираются по ID хостов, группам, точным названиям, префиксу или регулярному
выражению по итоговому названию после подстановки переменных. Xray также поддерживает
группы хоста-получателя. Для источника сохраняются собственные инбаунд, адрес,
переопределения и учётные данные протокола. Выбор не обходит права пользователя
и выключенные форматы. Стратегии и проверки доступности задаются нативными
полями клиентской конфигурации. Служебные директивы удаляются перед выдачей.
Директивы задаются прямо в тексте шаблона через объект `marzban`. JSON-редактор
показывает подсказки и проверяет их типы, значения и расположение по схеме backend.
Предпросмотра и отдельных полей выбора источников нет. Clash сохраняет поддержку
YAML/Jinja; схемы с описаниями и подсказками доступны для Xray JSON, Clash в JSON/YAML,
sing-box и Outline. Для URI и остальных шаблонов доступны подсказки переменных Jinja.
Исходный Jinja проверяется сервером после рендеринга. При переносе старых
балансировщиков текст шаблонов сохраняется без служебных Jinja-обёрток;
сохранённые настройки переноса применяются backend после рендеринга и сохраняются
при редактировании и клонировании шаблонов.

Если формат выключен для хоста, этот хост не выдаётся в данном формате. Если подходящих
хостов нет, панель возвращает пустой ответ `204`. Для общих форматов необязательный
`template_id` в ссылке имеет приоритет над default. Привязки, порядок хостов и наличие
инжекта не участвуют в выборе общего шаблона и не вызывают конфликтов `409`.
Составной default Clash или sing-box может включать только скрытые источники;
обычные шаблоны без выбранных подключений остаются пустыми.
Подробный контракт описан в [документации шаблонов](docs/subscription-templates.md).
Модель, API и перенос данных описаны в [документации хостов](docs/hosts.md).

### Диагностика и эксплуатация

Администратор проверяет состояние соединения с нодами, их ошибки и версию Xray,
просматривает runtime-логи и статистику трафика. Профиль ноды объединяет её параметры,
инбаунды, аутбаунды, маршрутизацию и логи.

Панель поддерживает выпуск и обновление сертификатов через ACME на ноде с передачей
результата в master-панель. Для обслуживания установки доступны резервные копии базы
и полные резервные копии, восстановление, административный CLI и скрипты обновления.

## Возможности интерфейса

Основные разделы dashboard — пользователи, статистика, ноды и их профили, хосты,
шаблоны подписок и настройки. Инфраструктурные разделы и общие настройки требуют
прав sudo-администратора. Редактирование инбаундов, аутбаундов и маршрутизации доступно
в контексте ноды; REST API также предоставляет операции с конфигурационными сущностями.

Панель включает поиск и фильтры пользователей, сохранение фильтров в URL, массовый
сброс трафика, сортировку хостов и правил маршрутизации, редакторы JSON-конфигурации
с валидацией и автодополнением. Поддерживаются светлая и тёмная темы, локализации
на английском, русском, персидском и китайском языках.

## Принципы поведения продукта

- **Явные изменения инфраструктуры.** Назначения на ноды и доступные форматы подписки должны оставаться понятными администратору.
- **Сохранение существующих привязок.** Изменение значения по умолчанию не переназначает уже настроенные хосты.
- **Предсказуемая выдача подписок.** Выключенный формат не включается автоматически при выборе другого шаблона или приложения.
- **Ограничение области воздействия.** Изменения конфигурации применяются к затронутым узлам; права доступа проверяются на backend.
- **Сохранение данных при обновлениях.** Изменения схемы выполняются миграциями; перед обновлением и откатом нужны резервные копии.
- **Обратная связь в интерфейсе.** Формы показывают загрузку и ошибки, а действия с существенными последствиями требуют явного подтверждения.

Объекты, импортированные из `XRAY_JSON`, имеют ограничения read-only: их JSON нельзя
редактировать или удалить, при этом состояние, метаданные и назначения на ноды
остаются изменяемыми.

## Технические и эксплуатационные границы

Backend построен на FastAPI, SQLAlchemy и Alembic; dashboard — на React и TypeScript
с Vite, Tailwind CSS и shadcn. Поддерживаются SQLite, MySQL и MariaDB.
REST API используется dashboard и внешними интеграциями; Swagger UI включается настройкой `DOCS`.

Для серверной эксплуатации предназначены Linux и Docker Compose v2; релизные образы
публикуются для `amd64` и `arm64`. Windows поддерживает локальную разработку панели
и dashboard. Xray-узлы разворачиваются отдельно от master-панели.

При запуске Docker-образа миграции выполняются перед стартом backend. При запуске
из исходников их нужно применить отдельно. Откат к старой версии приложения должен
учитывать совместимость схемы БД и возможную потерю данных при downgrade.
